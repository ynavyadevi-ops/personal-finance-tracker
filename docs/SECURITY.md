## 1. Security Overview & Threat Model

Financial management systems handle confidential personal and financial records. The architecture treats security as a foundational invariant, establishing defense-in-depth across the presentation, API, service, and persistence layers.

## 2. OWASP Top 10 Mitigation Matrix

| OWASP Risk | Threat Description | Architectural Mitigation in Python + SQL Stack |
| :--- | :--- | :--- |
| **A01: Broken Access Control** | Unauthorized user accesses another user's accounts, transactions, or budgets. | **Strict Tenant Query Scoping**: Every SQLAlchemy query executes with a mandatory `where(Model.user_id == current_user.id)` predicate. FastAPI dependency injection ensures unauthenticated or cross-tenant requests return 401 or 404 immediately. |
| **A02: Cryptographic Failures** | Exposure of passwords, sensitive tokens, or unencrypted data in transit. | **Strong Cryptography**: TLS 1.3 enforced in production. Passwords hashed using **Argon2id** (or bcrypt) with calibrated memory and iteration costs. JWT tokens signed with strong secrets (`HS256` or `Ed25519`). |
| **A03: Injection** | SQL injection, command injection, or script injection via malformed input. | **SQLAlchemy Parameterization & Pydantic**: 100% of database queries use SQLAlchemy ORM or parameterized Core statements. Zero raw SQL string concatenation. Pydantic v2 strips unexpected fields and validates data types. |
| **A04: Insecure Design** | Flawed business logic enabling unauthorized balance generation or race conditions. | **Double-Entry Balance Conservation & Atomic DB Transactions**: Inter-account transfers execute within atomic `session.begin()` blocks. Floating-point arithmetic is forbidden; all calculations use `decimal.Decimal`. |
| **A05: Security Misconfiguration** | Insecure default configs, unhardened headers, exposed debug endpoints. | **Security Headers & CORS**: FastAPI configures explicit trusted CORS origins. In production, security headers (`Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`) are enforced. |
| **A06: Vulnerable Components** | Dependencies with known CVEs or supply-chain malware. | **Automated Audits**: Mandatory execution of **`pip-audit`** in CI pipelines to scan against the PyPI vulnerability database. Dependency additions require strict vetting. |
| **A07: Identification & Auth Failures** | Brute force attacks, session hijacking, or credential stuffing. | **Rate Limiting & Secure JWT**: Rate limiting on `/api/v1/auth/*` routes; explicit token expiration; revocation tracking; short token lifetimes. |
| **A08: Software & Data Integrity Failures** | Unverified packages or tampering with serialized data. | **Pinning & Hash Verification**: Dependencies pinned in `pyproject.toml` or `requirements.txt` with SHA-256 hashes generated by `uv` / `pip-tools`. Immutable audit log records for financial state modifications. |
| **A09: Security Logging & Monitoring Failures** | Breaches undetected due to missing or inadequate logs. | **Structured Security Logging**: Centralized logging for authentication failures, permission denials, and critical financial mutations. Zero PII/financial secrets in log outputs. |
| **A10: Server-Side Request Forgery (SSRF)** | Exploitation of export/import or webhook services to probe internal networks. | **Disabled Outbound Network Calls**: The backend does not make outbound network requests based on user input. CSV and Excel imports are processed strictly in-memory from uploaded file buffers. |

## 3. Static Application Security Testing (SAST) with Bandit

**Bandit** is integrated into the development workflow to scan Python Abstract Syntax Trees (AST) for common security weaknesses:

```bash
# Run Bandit across the entire Python codebase
bandit -r src/ -ll -ii
```

### Prohibited Code Constructs Flagged by Bandit
1. **`B608` (SQL Injection)**: Direct string formatting into SQL queries. (Must use SQLAlchemy parameterized statements).
2. **`B105`, `B106`, `B107` (Hardcoded Passwords/Tokens)**: Hardcoded secrets in code. (Must use Pydantic `BaseSettings` / environment variables).
3. **`B301`, `B403` (Insecure Deserialization)**: Usage of `pickle` is strictly forbidden. (Use JSON or Pydantic models).
4. **`B311` (Weak Randomness)**: Use `secrets` instead of `random` for cryptographic tokens.
5. **`B110`, `B112` (Try-Except-Pass)**: Silent exception suppression is forbidden.

## 5. Environment Variables & Secret Management

1. **Pydantic BaseSettings Integration**:
   - Environment variables are loaded and validated at boot using `pydantic-settings`:
   ```python
   from pydantic_settings import BaseSettings, SettingsConfigDict
   from pydantic import SecretStr

   class Settings(BaseSettings):
       model_config = SettingsConfigDict(env_file=".env", env_file_encoding="utf-8")
       
       DATABASE_URL: str = "sqlite+aiosqlite:///./data/finance.db"
       SECRET_KEY: SecretStr
       ACCESS_TOKEN_EXPIRE_MINUTES: int = 60
       ENVIRONMENT: str = "development"
   ```
2. **Strict File Isolation**:
   - `.env.example` provides non-sensitive template configurations and is tracked in Git.
   - `.env`, `.env.production`, and any files containing actual keys are strictly excluded via `.gitignore`.
3. **Production Secret Injection**:
   - In production environments (Docker, AWS, GCP, Render), secrets must be injected as environment variables via cloud secret managers (e.g., AWS Secrets Manager, GitHub Secrets).

## 6. Database Access & Financial Data Protection

1. **Principle of Least Privilege**:
   - In production PostgreSQL, the application connects via a dedicated application role granted only `SELECT`, `INSERT`, `UPDATE`, `DELETE`.
   - DDL schema modifications are restricted strictly to Alembic migration executions.
2. **Monetary Precision Defense**:
   - IEEE 754 floating-point inaccuracies represent a security and financial integrity threat.
   - All financial math is protected by Python `decimal.Decimal` and database `Numeric(18, 2)` constraints.
3. **Database Backup Security**:
   - Automated database backups must be encrypted at rest using AES-256.
   - Database connection strings must enforce SSL encryption (`sslmode=require`).

## 8. Phase 2 Database Security & Data Integrity Safeguards

The Phase 2 database modeling implementation establishes multi-layered integrity defenses:

1. **Engine-Level Check Constraints**:
   - `chk_transactions_positive_amount`: Enforces `amount > 0` on transaction events.
   - `chk_transaction_entries_positive_amount`: Enforces `amount > 0` on ledger line items.
   - `chk_budgets_valid_month`: Rejects invalid calendar months (`1 <= month <= 12`).
   - `chk_budgets_positive_amount`: Rejects non-positive budget allocations (`amount > 0`).
   - `chk_savings_goals_positive_target` & `chk_savings_goals_non_negative_current`: Guarantees target is positive and current savings never dip below zero.
   - `chk_loan_debts_positive_principal`, `chk_loan_debts_non_negative_remaining`, `chk_loan_debts_non_negative_interest`, `chk_loan_debts_positive_term`: Prohibits corrupt financial liability structures.
   - `chk_holdings_non_negative_qty`, `chk_holdings_non_negative_cost_basis`, `chk_holdings_non_negative_total_cost`: Prevents negative portfolio quantities or costs.
   - `chk_inv_tx_non_negative_qty`, `chk_inv_tx_non_negative_price`, `chk_inv_tx_non_negative_amount`, `chk_inv_tx_non_negative_fees`: Validates investment ledger invariants.

2. **Foreign Key Deletion Restrictions (`RESTRICT`)**:
   - `transaction_entries.account_id` uses `ON DELETE RESTRICT` to prevent deleting any financial account that contains historical double-entry ledger lines.
   - `loan_debts.account_id` uses `ON DELETE RESTRICT` to prevent deleting accounts tied to active loans.
   - `investment_holdings.account_id` and `investment_holdings.asset_id` use `ON DELETE RESTRICT` to protect active positions from orphan deletions.
   - `investment_transactions.account_id` and `investment_transactions.asset_id` use `ON DELETE RESTRICT` to preserve immutable trade histories.

3. **Tenant Scoping & Cascading Erasure**:
   - Every domain table references `users.id` via `ON DELETE CASCADE`. If a user account is deleted, all personal financial data is completely erased from all 12 tables in a single cascade, preventing orphan data remnants.

4. **Immutable Audit Trail (`audit_logs`)**:
   - Dedicated `audit_logs` table stores JSON snapshots of state mutations (`old_values`, `new_values`), action type, timestamp, IP address, and user agent.
   - The table does not expose update or delete relationships, ensuring audit record immutability.

## 9. Phase 3 Service-Layer Security & Accounting Invariants

The Phase 3 domain service layer implements defense-in-depth security policies:

1. **Multi-Tenant Access Enforcement**:
   - Every service operation accepts and validates the authenticated `user_id`.
   - In `TransactionService.record_transfer`, both `source_account_id` and `destination_account_id` are independently validated for `account.user_id == user_id`, preventing cross-tenant transfer injection.
   - `CategoryRepository` validates that assigned categories belong to the authenticated user or are global system categories (`user_id is None`).

2. **Double-Entry Mathematical Conservation**:
   - `LedgerService.validate_balanced_entries()` verifies that total debits equal total credits for multi-leg transactions.
   - Inter-account transfers atomically produce 1 debit and 1 credit of equal amount.

3. **Idempotency Protection Against Replays**:
   - Submitting duplicate transaction requests with the same `idempotency_key` returns the cached transaction without duplicating financial records or balances.

4. **Currency Safety**:
   - Cross-currency transfers between accounts of different currencies are rejected with `CurrencyMismatchError` (HTTP 422). The system strictly forbids silent conversion or balance relabeling.

5. **Security Inventory Boundary Checks**:
   - `InvestmentService` enforces `InsufficientUnitsError` when an attempt is made to sell more securities than currently held in the account.
   - `SavingsGoalService` prohibits withdrawing more savings than the accumulated balance.
   - `LoanService` prohibits overpayment of loans and verifies positive loan tenures.

## 10. Phase 4 Authentication, JWT Security & Data Portability Defenses

1. **Argon2id Password Hashing (`src/core/security.py`)**:
   - Implements modern Argon2id password hashing via `pwdlib[argon2]`.
   - Uses cryptographic salting and work factor memory bounds.
   - Password hashes are strictly excluded from API response schemas (`UserRead`) and backup exports.
   - Unsalted SHA-256 and fast general-purpose hashes are strictly forbidden.

2. **JWT Authorization & Token Security**:
   - Tokens issued with short 60-minute UTC expiration (`exp`), issued-at (`iat`), token classification (`type="access"`), and issuer verification (`iss="personal-finance-tracker"`).
   - Validated using secret key with `HS256`.
   - All financial endpoints derive identity from `get_current_user` (`current_user.id`), eliminating IDOR/BOLA vulnerabilities. Client-supplied `user_id` is never accepted.
   - Public account enrollment (`/api/v1/auth/enroll`) was identified as insecure and has been completely removed from public route registration and OpenAPI specifications.

3. **Secure Administrative Legacy Enrollment CLI (`src/cli/enroll.py`)**:
   - Initial password enrollment for pre-existing legacy accounts is strictly restricted to an administrative CLI executed locally on the host (`python -m src.cli.enroll --email <email>`).
   - CLI enforces:
     - Target user verification in the database prior to credential prompt.
     - **Anti-Overwrite Protection**: Accounts with existing passwords cannot be re-enrolled or overwritten.
     - Interactive masked password entry with confirmation (`getpass.getpass`).
     - Command-line arguments for passwords (`--password`) are strictly forbidden, preventing secrets in shell history or process tables (`ps`).
     - Explicit confirmation prompt (`[y/N]`) before database write.
     - Atomic commit and rollback on error.
     - Zero credential or hash leakage to stdout, stderr, or log streams.

4. **Spreadsheet Formula Injection Defense (CSV & Excel)**:
   - Exported cells starting with dangerous trigger characters (`=, +, -, @, \t, \r`) are automatically escaped by prefixing them with a single quote (`'`), preventing formula execution when opened in Excel or Calc.

5. **Statement File Upload Hardening**:
   - Ingestion enforces a 5MB maximum file size limit and a 1,000 row cap.
   - File formats restricted strictly to CSV and XLSX.
   - In-memory parsing via Pandas with no shell execution or external network calls.

6. **Backup & Restore Safety Policy**:
   - User-scoped JSON snapshots export all 11 domain models with exact Decimal string representations.
   - Password hashes and sensitive authentication secrets are strictly scrubbed from exports.
   - Per security directives, destructive restore (`mode="REPLACE_USER_DATA"`) is strictly disabled and not executable in Phase 4. Only dry-run schema validation is exposed.

## 12. Phase 5 Frontend Security & Session Defenses

The Phase 5 Streamlit frontend architecture enforces multi-layered UI security defenses:

1. **Strict In-Memory Session Storage (`st.session_state`)**:
   - Authentication tokens (`access_token`) and user profiles are stored exclusively in Streamlit's volatile server-side memory (`st.session_state`).
   - Tokens and credentials are never persisted to local storage, cookies, browser disk caches, or URL query parameters.
   - Plaintext passwords submitted during login are never saved to session state or cached in memory.

2. **Authentication Barrier & Automated Redirection**:
   - `src/frontend/app.py` enforces a mandatory authentication gate before rendering any navigation options or financial views.
   - Unauthenticated callers are immediately trapped in `render_login_view()`, with execution halted via `st.stop()`.

3. **Session Expiration & 401 Interception**:
   - All backend API interactions pass through the centralized `ApiClient`.
   - Any response carrying an HTTP 401 Unauthorized status automatically clears `access_token`, marks `session_expired = True`, and redirects the operator to the login portal with a clear warning notice.

4. **Zero Credential Leakage in Logging & UI**:
   - `ApiClient` constructs Bearer token headers programmatically without logging request payloads or tokens.
   - User interfaces strictly mask password inputs with `type="password"`.
   - Logging configurations filter out authorization headers and token payloads.

5. **Decoupled API Execution**:
   - Frontend views and widgets are completely decoupled from SQLAlchemy ORM models and SQLite database files.
   - All data fetching and mutations strictly execute through authorized FastAPI REST endpoints (`/api/v1/*`), ensuring that tenant isolation, double-entry mathematical balancing, and check constraints cannot be bypassed from the UI layer.

6. **Currency Display Separation**:
   - The UI enforces strict isolation of monetary amounts by currency (`format_money`).
   - Indian Rupee (INR) is enforced as the core default currency, while USD accounts are rendered accurately with the `$` symbol without silent conversion or unapproved summation.

## 14. Privacy-First AI Insights & Data De-identification Policy (Phase 7)

### 14.1 Core AI Security Principles
1. **Explicit User Opt-In (Disabled by Default)**:
   - AI financial insights are strictly disabled by default upon application initialization.
   - Requires explicit toggle activation by the authenticated user in the UI. Users may disable AI insights at any time.
2. **Zero PII & Credential Leakage**:
   - Before any metric payload is passed to AI synthesis routines, `PrivacySafeAiInsightsService.sanitize_for_ai_payload()` completely strips:
     - User UUIDs, names, and email addresses.
     - Account IDs, account numbers, and institution names.
     - Raw transaction descriptions and merchant identifiers.
     - Passwords, JWT access tokens, and API keys.
3. **Aggregated Proportions Only**:
   - The payload format is restricted strictly to high-level monthly income/expense totals and top-5 category percentage allocations (e.g. `{"monthly_income_band": "50000.00", "top_expense_proportions": [{"category": "Housing", "percentage": 45.0}]}`).
4. **Local Rule-Based Synthesis & Zero Outbound Calls**:
   - In adherence to Phase 7 scope boundaries, financial narratives are generated locally and deterministically.
   - Zero outbound HTTP/API calls are dispatched to external cloud AI vendors without explicit user consent and separate architectural approval.
5. **Mandatory Non-Advice Disclaimer**:
   - All AI-generated text is permanently paired with the notice:
     *"AI-assisted observations are generated for informational and planning purposes only, may contain inaccuracies, and do not constitute certified or regulated financial advice."*

## 15. Phase 8 System Hardening, Penetration Defenses & Final Security Audit

### 15.1 Penetration Defenses & Negative Security Invariants
1. **Multi-Tenant Authorization & Boundary Isolation**:
   - Cross-user tenant testing verifies that an authenticated user (User B) cannot inspect, modify, delete, or reverse financial resources owned by User A.
   - Cross-tenant queries return HTTP 404 (`Not Found`) rather than 403, preventing attackers from probing resource existence.
2. **Permanent Elimination of Public Enrollment**:
   - The insecure public endpoint `POST /api/v1/auth/enroll` was permanently removed in Phase 4 security remediation.
   - Automated regression test confirms `POST /api/v1/auth/enroll` returns HTTP 404 across all call patterns.
   - Account enrollment is accessible solely via local administrative CLI (`src/cli/enroll.py`) utilizing interactive masked password prompts and Argon2id hashing.
3. **Double-Entry & Reversal Idempotency**:
   - Repeated reversal attacks against the same transaction are strictly rejected with HTTP 422 (`ValidationError: Transaction has already been reversed`).
   - Transfer balance conservation guarantees that total monetary value across accounts remains equal during transfers and compensating reversals.
4. **Data Portability & Backup Tamper Protection**:
   - CSV exports sanitize trigger characters (`=`, `+`, `-`, `@`, `\t`, `\r`) by prepending a single quote `'` to neutralize formula injection in spreadsheet software.
   - Backup dry-run validation enforces schema versioning ("1.0.0"); invalid versions and malformed payloads are rejected.
   - Destructive restore (`REPLACE_USER_DATA`) is strictly non-executable and disabled.

## 16. User Registration & Administrative Portal Security Architecture

### 16.1 Anti-Enumeration & Registration Protection
1. **Generic Duplicate Error**:
   - `POST /api/v1/auth/register` returns generic message `ValidationError("Unable to complete registration with the provided details.")` when a duplicate email is provided.
   - Attackers cannot enumerate registered email addresses by probing registration responses.
2. **Password Complexity Invariant**:
   - Minimum 8 characters, maximum 128 characters.
   - At least 1 uppercase letter, 1 lowercase letter, 1 digit, and 1 special symbol.
3. **Argon2id Key Derivation**:
   - Passwords hashed using Argon2id with memory cost parameters matching existing security baselines.
   - Plaintext passwords never stored, cached, logged, or reflected in API responses.
4. **Sliding-Window Rate Limiting**:
   - Registration and authentication attempts are throttled by client IP (5 attempts per 15-minute window).
5. **Platform Kill-Switch**:
   - `registration_enabled` setting in `system_settings` table allows administrators to immediately freeze public registrations (returning HTTP 403 Forbidden).

### 16.2 Administrator Bootstrap & Governance Controls
1. **Local CLI Only**:
   - Initial administrative bootstrap requires physical/shell access via `python -m src.cli.bootstrap_admin`.
   - Public API cannot bootstrap administrators.
2. **Idempotency & Anti-Elevation Guard**:
   - CLI checks if an active admin already exists; aborts cleanly if so.
   - Standard `USER` accounts cannot be elevated to `ADMIN` without explicit, interactive operator confirmation.
3. **Mandatory First-Login Password Change**:
   - Bootstrapped or reset admin and user accounts receive `must_change_password=True`.
   - The user is gated by a blocking password change UI before any application features become accessible.
4. **Self-Disable Prevention**:
   - An administrator cannot deactivate their own active account (`ValidationError` -> HTTP 422).

### 16.3 Strict Financial Privacy Boundary
1. **Architectural Segregation of Admin & Financial Data**:
   - Administrative endpoints (`src/api/routers/admin.py`) and UI views (`src/frontend/views/admin.py`) interact exclusively with `User`, `AuditLog`, and `SystemSettings`.
   - Queries and joins against financial tables (`FinancialAccount`, `Transaction`, `Budget`, `SavingsGoal`, `LoanDebt`, `InvestmentHolding`) are strictly forbidden in administrative code paths.
   - Platform administrators cannot query, view, or deduce any customer balances, accounts, transactions, or financial holdings.
2. **Immutable Audit Trail**:
   - All administrative actions (`USER_STATUS_CHANGE`, `ADMIN_PASSWORD_RESET`, `SYSTEM_SETTINGS_UPDATE`, `ADMIN_BOOTSTRAP`) are immutably logged with actor admin ID, target entity ID, IP address, user-agent, and timestamp.
